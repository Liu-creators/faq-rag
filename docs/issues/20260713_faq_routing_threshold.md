# FAQ 路由阈值失效问题分析 (FAQ Routing Threshold Issue)

**日期:** 2026-07-13
**模块:** `src/faq_rag/services/ask/pipeline.py`

## 1. 问题描述
在当前的提问流水线（AskPipeline）中，使用向量相似度（Dense Retrieval）的硬阈值（如 `0.90 ~ 0.95` 之间判定为需要改写的 FAQ）来决定请求的路由分支。
这会导致在面对**“高语义相似度但核心实体冲突”**的场景时发生误判。

**典型 Case：**
*   **匹配到的 FAQ：** "macOS 环境下，如何升级ollama?"
*   **用户问题：** "linux 环境下，如何升级ollama?"

由于主干语义完全一致，仅操作系统实体不同，向量相似度极易落在 0.90-0.95 区间。这会触发“FAQ 锚定 LLM 改写”分支，从而**短路（Short-circuit）**了后续的文档 RAG 流程，导致系统用 macOS 的 FAQ 去强行回答 Linux 的问题。

## 2. 根本原因
*   **向量模型（Embedding）的实体钝感：** 双塔模型（Bi-encoder）捕捉的是整体语义，对局部核心实体（如 Linux vs macOS）的互斥关系缺乏敏感度。
*   **硬阈值路由（Hard Threshold Routing）的局限性：** 试图用单一维度的标量分数（相似度）来承载复杂的逻辑分支决策（用 FAQ 还是用长文档），粒度过粗。

## 3. 拦截策略的困境：为什么“打补丁”很难？

如果我们试图在当前架构下通过“字法相似度（Lexical Similarity / BM25 乘法惩罚）”等轻量级手段来打补丁，会面临极为棘手的两难困境：

*   **痛点 A (长句主语冲突):** 假设句子极长（例如 50 个词），其中 49 个词都完全一致，只有 1 个核心实体（比如 "Linux" vs "macOS"）不同。此时，无论是向量相似度还是字法重叠度，其得分都会极高，轻量级惩罚机制根本无法将分数拉下阈值，依然会导致错误改写。
*   **痛点 B (同义转述误杀):** 用户问题仅仅是 FAQ 的一种不同表达方式（例如 FAQ 是“如何更新您的账户密码”，用户问“怎么修改我的登录密令”）。此时核心意图完全一致，理论上这是 LLM 改写的最佳适用场景。但如果引入了字法惩罚机制，因为字面重叠度极低，会导致分数被大幅拉低，从而未能命中 FAQ 改写，反而退化到更昂贵的文档 RAG。

**结论：** 传统的统计算法（无论是向量空间还是字法匹配），都无法真正理解**“什么是关键的互斥主语实体”**与**“什么是无伤大雅的同义替换”**。它们只能给出整体的相似度，无法做逻辑上的判别。

## 4. 潜在解决方案及优缺点

### 方案一：LLM 裁判路由 (LLM-as-a-Judge) [推荐]
在命中 Top-1 FAQ 后，不再仅凭分数判定，而是插入一次极小的 LLM 调用（如结构化输出或小模型），询问：“用户问题是 X，FAQ是 Y。该 FAQ 能否解答该特定环境的问题？YES/NO”。
*   **优点：** 彻底解决实体冲突。只有 LLM 能同时处理“长句互斥实体识别”（判 NO）和“同义转述识别”（判 YES）。
*   **缺点：** 增加一次 LLM 调用的延迟和 Token 成本。

### 方案二：引入 Reranker (交叉编码器重排)
引入如 BGE-Reranker 等 Cross-encoder 模型，对召回的 Top-K FAQ 进行重排。
*   **优点：** 对实体不一致敏感，能有效识别出冲突并打出低分；推理速度快于外部 LLM。
*   **缺点：** 架构变重；处理长文本或复杂逻辑时，泛化能力仍弱于 LLM。

### 方案三：晚期融合机制 (Late Fusion) [终极演进方向]
废弃瀑布流短路逻辑，并行检索 FAQ 和 Doc 库，将最高分的 FAQ 和 Top-K 文档片段一并交给最终的 LLM，由 LLM 决定是依赖 FAQ 还是依赖长文档来回答。
*   **优点：** 架构最干净，彻底消灭路由阈值，上下文最丰富，容错率极高。
*   **缺点：** 每次提问都需要全量检索长文档库，消耗更多 Token；可能削弱高分 FAQ 的绝对“一字不差”控制力。

## 5. 后续跟进建议
当前阶段建议先维持现状。在后续迭代中：
1.  **短期：** 优先考虑 **方案一（LLM裁判）**。因为无论是“只有核心主语不同的长句”还是“完全不同的表达但意思相同”的场景，这都属于典型的自然语言推理问题，只有 LLM 能够准确且优雅地处理。
2.  **长期：** 考虑向 **方案三（晚期融合）** 演进，彻底解耦检索与最终的决策链路。
